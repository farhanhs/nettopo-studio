# NetTopo Studio 開發計畫

建立日期：2026-07-28

本文件用來記錄後續要開發的功能、候選套件/ability、導入順序與自動測試方向。開發實作細節仍寫在 `docs/dev開發紀錄/`，測試結果與資料落差仍寫在 `docs/dev測試紀錄/`。

## 目前要加入計畫的事項

1. 多重設備拓樸設定以及儲存
   - 目標：同一頁可以切換不同客戶、不同場域、不同版本的設備架構。
   - 例：興恆毅 / A 分店 / 更新後拓樸、另一客戶 / 總公司 / 現況拓樸。
   - 進度：2026-07-28 已完成第一版，導入 Dexie.js + Zustand，支援客戶/拓樸切換、新增客戶、新增拓樸與 IndexedDB 自動儲存。

2. 新增文件匯入一鍵生成架構圖
   - 目標：匯入 TXT、Markdown、CSV、DOCX、圖片或 PDF 後，自動生成拓樸草稿。
   - 必須輸出「不確定事項清單」，不能把缺資料的地方靜默亂猜。

3. 反向將設置好的設備網路架構生成並輸出設定文件
   - 目標：從 app 內的 Project 生成 CSV。
   - 至少輸出：
     - devices.csv
     - links.csv
     - groups.csv
     - credentials.masked.csv
     - missing-info.csv

4. 設計美化 UI 的快速樣板及拓樸圖面優化
   - 目標：讓拓樸圖更像可交付給客戶的架構圖。
   - 包含：圖面樣板、節點類型圖示、群組容器、線條避讓、PDF 橫向輸出、數量型節點。

## 候選套件 / ability 分析

| # | 套件 / ability | 對應功能 | 優點 | 風險 / 注意 | 建議 |
|---:|---|---|---|---|---|
| 1 | Dexie.js | 多客戶、多拓樸、本機 IndexedDB 儲存 | 比 localStorage 更適合多筆資料、索引、版本、查詢；可搭配 React hooks | 需要設計資料庫 schema 和 migration | 優先導入 |
| 2 | Zustand | app 狀態管理、多拓樸切換、UI 狀態 | 輕量，適合把 Project、selectedCustomer、selectedTopology、dirty state 從單一 page state 拆出 | 不能取代資料庫，只負責記憶體狀態 | 優先導入 |
| 3 | React Flow JSON / viewport save | 儲存畫布節點、邊、viewport | React Flow 官方支援 JSON-compatible flow；適合保存縮放、平移、節點位置 | 目前 app 有 domain model，需要定義 domain Project 與 React Flow JSON 的轉換邊界 | 優先導入概念，不一定新增套件 |
| 4 | Zod 或 Ajv | 匯入資料 schema 驗證 | 匯入文件/JSON/CSV 後先驗證，避免壞資料進入 Project | Zod 適合 TypeScript domain schema；Ajv 適合 JSON Schema/CLI 驗證 | 優先導入 Zod；若需要公開 JSON Schema 再加 Ajv |
| 5 | Papa Parse | CSV 匯入/輸出 | 可 parse CSV、local file，也可 `unparse` JSON to CSV；適合 browser local-only | 複雜 Excel/xlsx 不適合，只處理 CSV | 優先導入 |
| 6 | SheetJS | Excel/CSV/XLSX 進階匯入輸出 | 能讀寫 spreadsheet，適合未來處理客戶給的 Excel 設備表 | 比 Papa Parse 重；部分授權/功能要注意 CE vs Pro 邊界 | 第二階段導入 |
| 7 | Mammoth.js | DOCX 文件匯入 | 可把 Word/Google Docs 匯出的 docx 轉 HTML 或 raw text，適合讀設備交接文件 | 不保證複雜版面準確；需注意不可信文件安全 | 第二階段導入 |
| 8 | Tesseract.js | 圖片架構圖 OCR / 掃描文件 | 可從圖片中擷取文字，適合使用者上傳架構圖或照片時輔助辨識 | OCR 結果不穩，不能直接當真；需人工確認 | 第三階段導入，先做輔助不是全自動 |
| 9 | dom-to-image-more 或 html2canvas | 拓樸圖面輸出 PNG / PDF 前置圖像 | 可把 DOM/拓樸區轉成 PNG/SVG/JPEG，方便客戶交付與 PDF 排版 | DOM 截圖不一定 100% 還原，尤其外部資源/字型/SVG | 優先評估 dom-to-image-more，html2canvas 作備選 |
| 10 | @react-pdf/renderer | 產生正式 PDF 報告/設定文件 | 可用 React 組 PDF，一頁 A4 橫向、封面、設備表、連線表都可控 | 和目前 `window.print()` 是不同路線；拓樸圖可能仍需先轉成圖片 | 第二階段導入 |

## 建議導入順序

### 第一階段：資料層與多拓樸

目標：先把「單一 localStorage 專案」升級成「多客戶/多拓樸」。

建議導入：

1. Dexie.js
2. Zustand
3. React Flow JSON / viewport save
4. Zod

預計資料表：

```ts
customers: {
  id: string;
  name: string;
  notes?: string;
  createdAt: string;
  updatedAt: string;
}

topologyProjects: {
  id: string;
  customerId: string;
  name: string;
  versionLabel: string;
  project: Project;
  viewport?: { x: number; y: number; zoom: number };
  createdAt: string;
  updatedAt: string;
}
```

UI 變更：

- 左上或上方工具列新增客戶/拓樸切換器。
- 新增「建立客戶」、「建立拓樸」、「複製目前拓樸」、「刪除拓樸」。
- 儲存狀態從「瀏覽器本機儲存」改成「已儲存到本機資料庫」。

自動測試：

- 建立兩個客戶，各兩個拓樸。
- 切換客戶時，畫面設備與連線必須跟著切換。
- 拖曳節點後切換回來，位置要保留。

### 第二階段：匯入/匯出

目標：讓資料能進出系統，開始真正像工具。

建議導入：

1. Papa Parse
2. Zod
3. Mammoth.js
4. SheetJS

匯入流程：

1. 使用者選擇檔案。
2. 系統辨識檔案類型：TXT / Markdown / CSV / DOCX / XLSX。
3. 解析成中介格式 `ImportedTopologyDraft`。
4. 用 Zod 驗證。
5. 顯示確認頁：
   - 已識別設備
   - 已識別連線
   - 已識別 SSID
   - 缺資料問題
   - 帳密遮蔽結果
6. 使用者確認後才寫入 Project。

匯出 CSV：

- `devices.csv`
- `links.csv`
- `groups.csv`
- `credentials.masked.csv`
- `missing-info.csv`

自動測試：

- 匯入標準範本 Markdown，產出固定 Project。
- 匯入 CSV，確認設備/連線筆數。
- 匯出 CSV 後再匯入，確認資料可 round-trip。
- 含密碼輸入不得輸出明文。

### 第三階段：圖面與 PDF 交付

目標：讓拓樸圖可以變成漂亮的交付文件。

建議導入：

1. dom-to-image-more
2. @react-pdf/renderer
3. Tesseract.js

圖面能力：

- 節點樣板：
  - Internet cloud
  - modem
  - router
  - firewall
  - switch
  - mesh-node
  - ssid
  - printer
  - camera
  - POS
  - PC/tablet/phone/IoT
- 群組容器：
  - site
  - VLAN
  - SSID
  - floor/area
- 數量型節點：
  - `iPad x5`
  - `Google Home x5`
  - `Camera x5`
- 圖面模式：
  - 技術圖
  - 客戶簡報圖
  - 施工/交接圖

PDF 輸出：

- A4 橫向一頁拓樸圖。
- 附錄設備表。
- 附錄連線表。
- 遮蔽帳密表。
- 缺資料確認表。

自動測試：

- PDF 必須是 A4 landscape。
- 拓樸圖不得被裁切。
- 多頁報告要有頁碼與標題。
- 匯出 PNG/PDF 的節點數與 app 畫面一致。

## 建議立即導入的套件

下次開發建議優先處理這 5 個：

1. Dexie.js
   - 理由：多客戶、多拓樸儲存是後續所有功能的資料基礎。

2. Zustand
   - 理由：目前 `app/page.tsx` state 已經太集中；先拆狀態，後面匯入/匯出會比較穩。

3. Zod
   - 理由：匯入資料一定要驗證，尤其是客戶文件來源不穩定。

4. Papa Parse
   - 理由：CSV 匯入/匯出是最直接、最實用的資料交換格式。

5. dom-to-image-more
   - 理由：圖面輸出和 PDF 報告都需要穩定取得拓樸區影像。

暫不優先：

- Tesseract.js：OCR 對架構圖很有用，但準確度不穩，應放在「輔助辨識」階段。
- SheetJS：等 CSV 流程穩定後再支援 Excel。
- Mammoth.js：等標準範本與 CSV 路線穩定後，再支援 docx。
- @react-pdf/renderer：等拓樸影像輸出穩定後，再做正式 PDF 報告。
